# Workagent

Workagent is a persistent general agent in a shared, editable workspace. Conversation,
native artifacts and ongoing responsibilities belong together: delegate unfamiliar work,
correct the result directly, redirect it and return to useful progress.

The canonical product direction is:

1. [Product blueprint](docs/product/01-product-blueprint.md) — complete P01–P16 scope and experience.
2. [Architecture](docs/product/02-architectural-plan.md) — selected technical design and unproven seams.
3. [Build steps](docs/product/03-build-steps.md) — concrete delivery units, actual dependencies and checks.

Read [development direction](docs/DEVELOPMENT_AUTHORITY.md),
[model spending](docs/GENERAL_MODEL_AUTHORIZATION.md), [ownership](AGENTS.md) and
[STATUS](STATUS.md) before work. The owner's START activated B01, followed by B02 and
B03 as their technical prerequisites permit, including routine reversible implementation,
integration, feature-branch publication and private test-server operation. Implementation
checkpoints are not installed or demonstrated product outcomes; STATUS records the distinction.

The published DSH rc1 slice is scripted compatibility evidence. The previous owner UX
was rejected; its three services were stopped and disabled at the last verified check.
They stay stopped under current direction. Historical launchers, review/access notes,
alpha designs and handoffs remain records for their named installations, outside current
startup routing. New-product commands and private setup are in the
[runtime README](apps/workagent-server/README.md); code availability is not deployment.

The first useful outcome being implemented is a real DSH/model result in one
genuinely editable sheet or document, followed by a human correction and useful agent
continuation. Steering/restart and a responsibility with all clients closed follow before
broad office/data-suite completion. Full scope remains in the blueprint.

Codex/Astra owns frontend and backend implementation. Parent Hermes owns integration,
publication, test-server operations, accounting, paid calls and browser verification.
Worker sandbox restrictions do not revoke Parent's separately authorized work. Delivery uses one writer per
stream, proportionate changed-behavior checks and at most one useful risk review.

[Working boundaries](docs/WORK_CONTRACT.md) and [product evaluation](docs/PRODUCT_ACCEPTANCE.md)
retain the human-edit, isolation, recovery and truthful-evidence principles. Current
spending follows the unchanged model authorization and actual accounting; no balance is
inferred from historical grant summaries.

The obsolete `development-boundaries` workflow is preserved byte-for-byte in
[retired workflows](.github/retired-workflows/development-boundaries.yml), outside Actions.
Its $100 inventory/checker is historical tooling, not current financial governance.
Runtime financial/isolation/receipt tests remain intact. Legacy frontend CI remains
unchanged; the new client has a targeted workflow, whose actual execution is reported separately.
