## Prevent authority drift

1. **One controlling interpretation:** use this file and GENERAL_MODEL_AUTHORIZATION, not accumulated historical task-body prohibitions. New task bodies reference these files and contain only their execution specifics. Remove contradictory old wording instead of stacking another override on it. Completed task receipts remain historical.
2. **Classify before stopping:** say whether the obstacle is an OWNER LIMIT, TECHNICAL FAILURE, or ENGINEERING SETTING. An owner-limit claim cites the actual instruction and affected action. A technical failure cites observed evidence and next repair. An engineering setting is normally adjusted by Hermes within existing authority, not sent back as an approval request. This is a reporting discipline, not a new permission gate.
3. **No silent promotion:** an assistant-selected timeout, trial amount, review preference, source pin or no-edit proof scope cannot become a permanent owner restriction. A read-only card limits that card, not all successors. A source manifest binds historical evidence, not a code freeze.
4. **Separate completion from permission:** full Batch2 acceptance and production release may be HOLD while implementation, test runtime operation and feature-branch publication continue. Every HOLD names its scope; do not use bare 'publication HOLD' to block all development.
5. **Risk-proportionate verification:** reuse accepted evidence and one appropriate independent review. No reflexive whole-suite rerun, repeated broad audit, extra review layer or per-slice reapproval without a concrete changed risk. Requirements remain full-scope; do not weaken assertions or relabel pending rows.
6. **Startup/handoff check:** re-read these files after context recovery; include the current task, actual remaining work, existing budget lineage and active successor/precise blocker. Verify task instructions do not reintroduce the forbidden approval gates. Keep current product progress ahead of growing policy paperwork.

This document does not declare the product accepted, change budget balances, activate a grant, deploy anything, or authorize deletion. Skill copies are reminders; staged/unapproved skill edits are not active enforcement. The repository instructions remain the durable task-local source.
