# Development evaluation

Evaluate the [canonical product](product/01-product-blueprint.md) to improve it and state
what works. Unfinished increments may be published with honest limitations within their
authorized scope. The current documentation cleanup runs no product acceptance journey.

For a meaningful implementation change, inspect the affected behavior, run proportionate
regression checks and exercise its ordinary user path. Use at most one useful independent
risk-focused review. Broaden tests for actual risk or unresolved failures; no mandatory
all-model/all-persona, two-stage/per-task review or full-suite-every-edit gate applies.

Judge the integrated product by whether a person can:

- Start unfamiliar work naturally, get a real useful editable result and continue it.
- Edit or change requirements without losing contributions or accepting stale overwrites.
- Leave, return or interrupt execution and understand what happened and comes next.
- Let a responsibility advance with all clients closed, within its actual authority.
- Find, understand and steer work on desktop and phone without learning the machinery.

Use varied work to expose accidental special cases, within the authorized data/spend
scope. Keep expected answers out of model context. Distinguish fixtures, real-model
execution, inspected evidence, owner reports and user acceptance. Emulated phone viewports
cannot prove physical-phone behavior; two-human collaboration needs actual identity and
convergence checks. Missing evidence limits that claim, not unrelated engineering.

Preserve human edits at authoritative mutation commit, or keep agent changes uncommitted
as proposals. Check the human-edit/agent-commit race when implementing that boundary.
Demonstrate durable recovery and propagation before claiming them. A fixture or tool return
alone cannot establish useful completion. Ordinary analysis needs no certified label;
only an authorized human can confer that designation.

Andrew rejected the previous experience. Evaluate the fresh client against the blueprint
and actual use, without requiring old designs. Record usefulness findings and remaining
limits briefly. Owner feedback informs acceptance; waiting for it is not a dependency for
independent authorized implementation or the next unit's technical work.
