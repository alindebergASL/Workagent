# Development evaluation

Use evaluation to improve the product and establish what works. This is build mode:
unfinished increments may be published and shown with honest limitations.

For a meaningful change, inspect the relevant code, run proportionate regression
checks, and exercise the affected ordinary user path. Use independent reviewers
and broader suites when the risk warrants them; no mandatory all-model/all-persona
gate precedes every demonstration.

Judge the integrated product by whether a person can:
- Start unfamiliar work naturally, get a useful result and continue the same work.
- Edit or change requirements without losing contributions or receiving stale results.
- Leave, return or interrupt execution and understand what happened and comes next.
- Let an ongoing responsibility advance within authority without prescribing recovery.
- Find, understand and steer work on desktop and phone without learning the machinery.

Use more than one kind of work to expose accidental special cases. Keep expected
answers out of model context. Distinguish tests actually run, inspected evidence,
owner reports and user acceptance. A fixture pass or correct tool return alone
does not prove useful goal completion.

Report engineering, usefulness and experience briefly, including failures.
Andrew has rejected the current experience; improvements need actual user-path
evidence. A passing example does not complete the broad mission.
