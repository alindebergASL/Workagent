# B3.4b bounded delegation — implementation scope

Single product-worker execution remains the default. This increment adds an **opt-in deterministic analysis-child profile**, not an embedded Hermes runtime, a mandatory orchestra or a paid specialist-model provider.

## Contract

- `delegation.analysis` / `delegate_analysis`: one independently useful bounded task, output contract, Python program and up to six immutable file inputs. The parent supplies intent and code, never authority. At most two child launches per run.
- The server intersects the parent run/grant/source/effect authority with the fixed local-confined processor selector. Children receive only their exact staged input subset and a bounded task manifest. No parent conversation, recalled memory, service environment, bearer, lease secret or credential reference is copied. No child accept, scope elevation, API access or nested delegation capability exists.
- The existing pinned gVisor service executes actual isolated child processes with the existing CPU/memory/wall/process/output limits and no network. It supplies no live child-model route. The service can serialize execution: no latency improvement is claimed.
- Every child reserves from the parent's existing cumulative tool account before dispatch. Verification consumes that account's local-compute capacity. Unknown outcomes retain reservations and block fresh relaunches; no refund or new child allowance is created. Paid-provider billing is not inferred from a zero-dollar local reservation.
- Child stdout is bounded strict JSON with duplicate-key/nonfinite-number rejection. The retained child attempt, proposal digest, source manifest, code/profile/stdout hashes, execution status/resources and cost remain available as evidence. The parent receives the proposal digest directly.
- `delegation.verify` / `verify_delegate`: inspect the exact child attempt/proposal, then execute separately authored checks against the original immutable inputs and child result. A passing receipt allows proposal assimilation. Explicit `passed:false` with executed checks records **discarded**, returns no proposal and permits useful recovery. Exceptions remain failures, not discard or success.
- Verification is **execution of parent-authored checks**, not an oracle for arbitrary goals or human acceptance. Production/model callers can author weak checks; the useful synthetic demonstration uses an independent Fraction implementation against Decimal child calculations. No semantic-proof claim is made.
- Draft-capable gateway operations and staged publication/reply paths cannot assimilate unresolved child proposals. This includes confined compute exports, not just ordinary file creation. Source/processor restrictions, generation, run fence, lease and cancel/revoke checks fence execution, observation visibility and late settlement. Revoked late results retain cost-only history, not usable output.
- Raw child observations are excluded from procedure-evidence admission. Even verified check evidence does not bypass the existing human-reviewed memory lifecycle.

## Client and persistence

Existing canonical tool-attempt endpoints carry child and verifier receipts. Native **Status → Tool activity** now presents bounded child status, parent checks, proposal, source/authority and cost in read-only inert text. No new web control or web implementation was added. Existing durable SQL attempt/event/checkpoint storage is reused; migration 068 is additive, with no new child credential store or queue framework. Predecessor migrations and saved human work are preserved.

## Explicit limits

- No paid product-model calls, private data access, new processor route, external business effect, deployment or default-branch merge.
- Not a general multi-model delegation engine. The deterministic profile is useful for independent exact-input analyses; real paid multi-agent usefulness remains a separate ledger-gated evaluation.
- Parent control and receipt/process checks do not establish causal learning benefit, full memory usefulness or Batch 3 completion.
- Full correction/forget/revoke/restore adversarial closure belongs to existing successor **B3.5a `t_df70d103`**.
